# Security notes

What the app does to stay safe when it is reachable from the internet, and what the deployment has to do.

## Accounts and sessions

- Passwords are hashed with bcrypt (cost 12). Login compares against a dummy hash when the email is unknown, so timing does not reveal registered addresses; whether a request is pending or denied is only revealed after the password matched.
- Sessions are signed JWTs (`jose`, HS256) in an `httpOnly`, `SameSite=Lax` cookie, `Secure` in production, valid for seven days. Each token carries the account's session version; a password change bumps it, which logs every other device out.
- The placeholder session secrets in `.env.example`, the old compose default and the test configs are refused as soon as `APP_URL` is not localhost or `TRUST_PROXY` is set.
- The only way to an admin account is the setup code: bcrypt-hashed, burnt after five wrong guesses, rate limited per IP. A sign-up can never be more than a pending client. Demo profiles, whose passwords are public, are never admins, and `ALLOW_DEMO_LOGIN=0` disables their logins.
- Review rights (who may approve, deny or re-role whom) are checked in the data layer inside the transaction that reads the target's role, not only in the UI.

## Rate limits

- Wrong login guesses are limited per IP (10 per 15 minutes) and per account (20 per hour), so neither spoofing `X-Forwarded-For` nor spreading guesses over addresses helps. A right password spends neither budget.
- Sign-ups, the setup form and the click redirect are limited per IP; uploads and preview fetches per user. The sign-up form stops taking requests once 100 are waiting.
- Mail goes through an outbox with a rolling daily and hourly budget (`MAIL_DAILY_LIMIT`, `MAIL_HOURLY_LIMIT`), counted in addresses from what was actually sent, so a flood of sign-ups cannot spend the provider's quota: the admins' notice is one message however many requests arrive, and new requests are capped at 20 a day across all addresses. Sign-up addresses are not verified, so a decision mail can bounce; "Spam" declines without one, and a bounced address is never retried. Mail is sent with STARTTLS required unless `SMTP_TLS=none`.
- Password reset: the "forgot password" form gives the same answer for every valid address, and the lookup runs after the response, so neither the text nor the timing tells whether an account exists. Only approved accounts get a link. The token is 32 random bytes; only its SHA-256 is stored, the link works once and for 30 minutes, the page sends no referrer, and using it bumps the session version. A password change from the account page voids open links. Limits: one open link per account and three a day, five requests an hour per IP, twenty reset mails a day for the whole site. Reset mails go out ahead of other mail, are dropped if they cannot go out within 15 minutes, and their text is wiped from the outbox once sent.
- `TRUST_PROXY` says which header carries the visitor's address. It is only safe when nothing but that proxy can reach port 3000, which is why compose publishes the port on `127.0.0.1`.

## Input

- Link URLs are `http(s)` only; `javascript:`, `data:` and friends are rejected server-side. Social icon URLs are built by the app from a validated handle or address.
- Theme tokens pass a strict schema (6-digit hex colours, enum values, one bounded number) and the page only reads the CSS variables built from them, so a theme cannot smuggle `url()` or expressions into a style attribute.
- Uploads are capped at 5 MB, must be PNG, JPEG, WebP or GIF by their first bytes, and are always re-encoded: what is stored and served is a WebP the server produced. Every other libvips decoder (SVG, AVIF/HEIF, PDF, TIFF, JPEG 2000) is switched off in `sharp` for the whole process, so a crafted file in one of those formats never reaches a parser. Next's image optimisation endpoint is disabled.
- Storage keys are generated by the app and the image route serves only keys of that shape.

## Fetching a link's preview image

The server fetches a URL the owner typed, the classic SSRF shape. Only `http(s)`; no credentials in the URL; hostnames must resolve to public addresses, checked inside the connection's own DNS lookup so a rebinding between check and connect cannot slip through; the opened socket's remote address is checked again, which also covers IP literals in every spelling (v4, v6, v4-mapped, NAT64); each redirect hop is re-checked; pages are capped at 1 MB, images at 8 MB, with an 8 s deadline; the bytes are re-encoded like any upload. Tests set `LINK_PREVIEW_ALLOW_PRIVATE=1` to reach local servers; production never does.

## Headers and dependencies

- Every response carries a Content Security Policy (`default-src 'self'`, no third-party origins, `object-src 'none'`, `frame-ancestors 'none'`, `form-action 'self'`), HSTS, `X-Frame-Options`, `nosniff`, a referrer policy, a permissions policy and `Cross-Origin-Opener-Policy`. Inline scripts and styles are allowed: a nonce-based policy would force every page to render per request and lose the cached public pages, and the app embeds no third-party code.
- `next`, `react` and `sharp` are pinned past the October 2026 Next.js security update and the December 2025 React Server Components RCE; Dependabot opens a weekly PR for the next ones. No `eval`, no `child_process`; `$queryRaw` appears three times, always as a tagged template. The container runs as an unprivileged user.
- Click records keep the referrer host only. No IP addresses or user agents are stored.

## Deploying

1. `SESSION_SECRET`: `openssl rand -base64 48`. Changing it logs every browser out once.
2. `APP_URL`: the public `https://` address. Cookies are `Secure` in production, so plain `http://` on anything but localhost cannot log in; terminate TLS in front.
3. `TRUST_PROXY`: `cloudflare` behind a Cloudflare Tunnel, `1` behind nginx, Caddy or Traefik.
4. `ALLOW_DEMO_LOGIN=0`.
5. Complete `/setup` before sharing the hostname: until the admin exists the site serves nothing, and the only way in is the code in your compose logs.
6. Real `S3_*` credentials if the bucket is reachable from outside the compose network. The compose SeaweedFS enforces none and is reachable only from the other containers.

**Cloudflare Tunnel** (how links.juume.site runs): `cloudflared` on the same machine points at `http://localhost:3000`, so the stack is reachable only through Cloudflare. Worth turning on in the dashboard: *Always Use HTTPS* and TLS 1.2 minimum, *Bot Fight Mode*, a rate-limiting rule on `/login` and `/signup`, and optionally a Zero Trust Access policy on `/dashboard`.

## Known limits

- The rate limiter and the page cache live in process memory. Several replicas would need Redis and a shared cache handler.
- Whether a username or email is taken is visible on the sign-up form; hiding it would need email delivery.
- An unknown username renders the not-found page with `noindex` but a `200` status: the static shell streams before the lookup runs.
- The gallery has no moderation beyond the owner's own unpublish and delete.
